**What was found, and the evidence.** DESIGN.md (*Models*, *Training*): "Each final run reports
whether it met the plateau criterion by its last checkpoint." The scorer writes this as
`met_plateau_criterion` per run, from `plateau(...)["met_at_last_checkpoint"]` in `metrics.py`.
That value tests the criterion at the last checkpoint only, and the criterion is only evaluated at
checkpoints on a multiple of 1,000 updates; when the last checkpoint is not one, the value is
`None`. The budgets are 1.5 times a plateau point (*Pilot rule*, step 5): `mlp` 73,500, `mlp-ms`
100,500, `contact_wm` 136,500 and `gru` 105,000. So the field would be `null` for every run of
`mlp`, `mlp-ms`, `contact_wm`, their twins, `blind` and `mlp-shortcut`, and a true or false only for
`gru` and `gru-twin`. In the 220 main runs' `run.json` files, `plateau.met_at_last_checkpoint` is
`None` in all 170 runs whose budget is off the 1,000-update grid. Found when summarising the main
runs from their `run.json` files (validation loss only). The 50 `gru` and `gru-twin` runs have a
true or false there. No earlier check caught it: the existing test of the criterion ends on a
multiple of 1,000, and the scoring rehearsal (`scripts/rehearse_scoring.py`) uses three checkpoints
at 10 to 30 updates, too few for the criterion to be evaluated, so the field was `null` for every
run there and the format check, which requires the key but not its value, passed.

No gate, reading, matching step or exclusion reads this field: matching uses the checkpoint closest
to V\*, and the exclusions use whether L_obs comes within 5% of V\*. The format check requires the
key but not its value, so the scorer would not have failed; the result would have lacked what
DESIGN.md says each run reports.

**The fix.** The scorer reports whether the run met the criterion at any checkpoint up to its last,
that is, whether it has a plateau point (`first_update_met` is not `None`), which is what "met the
plateau criterion by its last checkpoint" says. `metrics.py`, which training also uses, is not
changed, so every `run.json` written so far stays as it is. No rule, threshold or reading changes,
no data or run is affected, and nothing is retrained. A new test scores a budget off the
1,000-update grid: on the old code it gives `None` for every run, on the new code true for a run
that met the criterion (also when it later improved by more than 1% again) and false for one that
never did.
